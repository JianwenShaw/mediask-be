#### [C-1] 外部传入 traceId 未做任何校验和清洗，存在日志注入与响应头注入风险

- **严重度：** Critical
- **类别：** 安全/输入校验
- **位置：** `mediask-api/src/main/java/me/jianwen/mediask/api/filter/TraceIdFilter.java:26-33` (`doFilterInternal`)
- **审查角色：** cr-qa, cr-architect, cr-product
- **置信度：** high

**问题代码：**
```java
String traceId = request.getHeader(CommonConstants.HEADER_TRACE_ID);
if (!StringUtils.hasText(traceId)) {
    traceId = UUID.randomUUID().toString().replace("-", "");
}

MDC.put(CommonConstants.MDC_TRACE_ID, traceId);
MDC.put(CommonConstants.MDC_REQUEST_URI, request.getRequestURI());
response.setHeader(CommonConstants.HEADER_TRACE_ID, traceId);
```

**问题描述：**
TraceIdFilter 直接从 HTTP 请求头 `X-Trace-Id` 读取外部输入，未做任何校验（长度限制、字符白名单、换行符过滤），直接写入 MDC 和响应头。攻击者可以：
1. 注入包含换行符（`\r\n`）的 traceId，在日志中伪造新的日志行（Log Injection/Log Forging）
2. 注入超长字符串导致日志膨胀或内存压力
3. 注入特殊字符，如果日志被下游系统（ELK、Splunk）解析，可能造成解析错误或 XSS（日志管理界面）
4. traceId 直接回写到响应头且通过 `Result.traceId` 返回到 JSON 响应体中，恶意内容会传递给前端

**影响分析：**
攻击者可在日志中注入虚假日志条目伪造审计记录，可通过响应头注入进行 HTTP 响应拆分攻击（如果中间件/代理对 CRLF 处理不当），可通过超长 traceId 导致日志磁盘空间快速消耗。对于医疗系统，日志完整性和安全合规尤为重要。

**修复建议：**
对外部传入的 traceId 进行严格校验：限制最大长度（如 64 字符）、只允许字母数字和连字符、过滤控制字符。不合法时忽略并自动生成新的 UUID。

```java
private static final int MAX_TRACE_ID_LENGTH = 64;
private static final Pattern TRACE_ID_PATTERN = Pattern.compile("^[a-zA-Z0-9\\-]{1,64}$");

String traceId = request.getHeader(CommonConstants.HEADER_TRACE_ID);
if (!StringUtils.hasText(traceId) || !TRACE_ID_PATTERN.matcher(traceId).matches()) {
    traceId = UUID.randomUUID().toString().replace("-", "");
}
```

**关联位置：**
- `mediask-common/src/main/java/me/jianwen/mediask/common/result/Result.java:69` — traceId 从 MDC 读出后写入 JSON 响应体
- `mediask-api/src/main/java/me/jianwen/mediask/api/filter/TraceIdFilter.java:33` — traceId 回写到响应头

#### [C-2] MDC 上下文无法传播到 @Async 异步线程，traceId 在事件处理中丢失

- **严重度：** Critical
- **类别：** 并发安全/可观测性
- **位置：** `mediask-infra/src/main/java/me/jianwen/mediask/infra/config/AsyncConfig.java:22-33` (`eventTaskExecutor`)
- **审查角色：** cr-architect, cr-product
- **置信度：** high

**问题代码：**
```java
@Bean(name = "eventTaskExecutor")
public Executor eventTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(8);
    executor.setQueueCapacity(100);
    executor.setThreadNamePrefix("event-");
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(60);
    executor.initialize();
    return executor;
    // 缺少 executor.setTaskDecorator(new MdcTaskDecorator());
}
```

**问题描述：**
TraceIdFilter 将 traceId 放入 MDC（基于 ThreadLocal），但项目中 `AppointmentEventListener` 使用了 `@Async("eventTaskExecutor")` 在独立线程池中处理领域事件。MDC 基于 ThreadLocal 实现，异步线程无法自动继承父线程的 MDC 上下文。`eventTaskExecutor` 和 `scheduleSolverExecutor` 均未配置 TaskDecorator 来传播 MDC 上下文。项目文档 `MediAskDocs/docs/16-LOGGING_DESIGN` 中已明确推荐使用 MdcTaskDecorator。

**影响分析：**
异步线程（事件监听器、排班求解器等）中的所有日志都不会携带 traceId，`Result` 对象在异步上下文中构建时 traceId 也会为 null。在生产环境下排查问题时，无法通过 traceId 将请求链路与异步处理关联，严重影响可观测性。

**修复建议：**
在 AsyncConfig 中为所有 ThreadPoolTaskExecutor 配置 MDC 传播的 TaskDecorator。

```java
// MdcTaskDecorator.java
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();
        return () -> {
            try {
                if (contextMap != null) {
                    MDC.setContextMap(contextMap);
                }
                runnable.run();
            } finally {
                MDC.clear();
            }
        };
    }
}

// AsyncConfig.java 中添加:
executor.setTaskDecorator(new MdcTaskDecorator());
```

**关联位置：**
- `mediask-infra/src/main/java/me/jianwen/mediask/infra/config/AsyncConfig.java:38` — scheduleSolverExecutor 同样缺失 TaskDecorator
- `mediask-infra/src/main/java/me/jianwen/mediask/infra/event/AppointmentEventListener.java:28` — @Async 导致 MDC 丢失
- `mediask-common/src/main/java/me/jianwen/mediask/common/result/Result.java:69` — Result.ok() 依赖 MDC.get 获取 traceId

#### [C-3] SysException 处理将系统内部错误消息直接暴露给客户端

- **严重度：** Critical
- **类别：** 安全/敏感数据泄露
- **位置：** `mediask-api/src/main/java/me/jianwen/mediask/api/advice/GlobalExceptionHandler.java:35-39` (`handleSysException`)
- **审查角色：** cr-architect, cr-senior-dev, cr-qa, cr-product（全部4个角色均指出）
- **置信度：** high

**问题代码：**
```java
@ExceptionHandler(SysException.class)
public Result<Void> handleSysException(SysException ex) {
    log.error("系统异常: code={}, msg={}", ex.getCode(), ex.getMessage(), ex);
    return Result.fail(ex.getCode(), ex.getMessage());
}
```

**问题描述：**
SysException 被设计用于系统级错误（数据库异常、缓存异常、外部服务调用失败等），其 message 可能包含数据库连接信息、Redis 地址、SQL 语句片段、堆栈摘要等敏感信息。当前直接将 `ex.getMessage()` 返回给前端，违反了 SysException 类注释中"返回通用错误提示"的设计意图。对比通用 `handleOther(Exception)` 处理器返回的是固定的 `ErrorCode.SYSTEM_ERROR` 消息，不会泄露任何内部细节。

**影响分析：**
当 SysException 被抛出时，异常 message 中的技术细节（表名、列名、连接字符串、SQL 语句等）可能通过 API 响应泄露给外部用户，构成严重安全风险。

**修复建议：**
返回预定义的安全消息，不暴露内部细节。详细信息仅记录在日志中。

```java
@ExceptionHandler(SysException.class)
public Result<Void> handleSysException(SysException ex) {
    log.error("系统异常: code={}, msg={}", ex.getCode(), ex.getMessage(), ex);
    // 返回预定义的安全消息，不暴露内部细节
    return Result.fail(ErrorCode.SYSTEM_ERROR);
}
```

**关联位置：**
- `mediask-common/src/main/java/me/jianwen/mediask/common/exception/SysException.java:8-13` — 类注释说明用于系统级错误
- `mediask-api/src/main/java/me/jianwen/mediask/api/advice/GlobalExceptionHandler.java:100-103` — handleOther 正确返回固定消息

#### [M-1] 全局拦截 IllegalArgumentException 范围过广，可能掩盖框架/库错误并泄露内部信息

- **严重度：** Major
- **类别：** 异常处理/回归风险
- **位置：** `mediask-api/src/main/java/me/jianwen/mediask/api/advice/GlobalExceptionHandler.java:86-91` (`handleIllegalArgument`)
- **审查角色：** cr-architect, cr-senior-dev, cr-qa, cr-product（全部4个角色均指出）
- **置信度：** high

**问题代码：**
```java
@ExceptionHandler(IllegalArgumentException.class)
public Result<Void> handleIllegalArgument(IllegalArgumentException ex) {
    String message = ex.getMessage() == null ? "参数不合法" : ex.getMessage();
    log.warn("非法参数异常: {}", message);
    return Result.fail(ErrorCode.PARAM_INVALID.getCode(), message);
}
```

**问题描述：**
IllegalArgumentException 是 JDK 标准异常，不仅被业务代码使用，也大量被 Spring Framework、MyBatis-Plus、Jackson、JDK 标准库等抛出。全局拦截意味着：
1. Spring 内部的 IAE（如 Bean 初始化错误）会被静默降级为 400 参数错误
2. Domain 层值对象校验的英文 message（如 "Invalid schedule id"）会直接暴露给用户
3. 框架级异常可能包含内部实现细节（类名、方法名、SQL 片段）
4. 日志级别为 warn 而非 error，框架级异常可能被监控告警忽略

项目中有 28+ 处 `throw IllegalArgumentException`（ScheduleId、DoctorId、PatientId、TimePeriod 等），部分 Service 层已正确做了 catch 转换（如 AuthzApplicationService、ScheduleApplicationService）。

**影响分析：**
以前作为"系统繁忙"(9999) 返回的框架内部异常现在会返回 PARAM_INVALID(1003) 给客户端，错误码语义错误且可能泄露内部实现。

**修复建议：**
建议移除对 IllegalArgumentException 的全局拦截。Domain 层抛出的此类异常应在 Service 层边界 try-catch 并转换为 BizException（已有先例）。如果保留全局兜底，至少应返回固定消息、以 error 级别记录、附带堆栈信息。

```java
// 如果保留，至少做如下改进：
@ExceptionHandler(IllegalArgumentException.class)
public Result<Void> handleIllegalArgument(IllegalArgumentException ex) {
    log.error("未预期的IllegalArgumentException: {}", ex.getMessage(), ex);
    return Result.fail(ErrorCode.PARAM_INVALID.getCode(), "参数不合法"); // 固定消息
}
```

**关联位置：**
- `mediask-domain/.../valueobject/ScheduleId.java:20` — throw new IllegalArgumentException("Invalid schedule id")
- `mediask-domain/.../valueobject/TimePeriod.java:40` — throw new IllegalArgumentException("Invalid time period code")
- `mediask-infra/.../cache/GuavaLocalCacheService.java:76` — 基础设施层 IAE 也会被拦截
- `mediask-service/.../AuthzApplicationService.java:70` — 已有正确的 catch→BizException 转换

#### [M-5] TraceIdFilter @Component 与 SecurityConfig addFilterBefore 双重注册

- **严重度：** Major
- **类别：** 设计模式/潜在Bug
- **位置：** `mediask-api/src/main/java/me/jianwen/mediask/api/filter/TraceIdFilter.java:19` 及 `mediask-api/src/main/java/me/jianwen/mediask/api/config/SecurityConfig.java:53`
- **审查角色：** cr-architect, cr-product
- **置信度：** medium

**问题代码：**
```java
// TraceIdFilter.java
@Component  // Spring Boot 自动注册到 Servlet Filter Chain
public class TraceIdFilter extends OncePerRequestFilter { ... }

// SecurityConfig.java
.addFilterBefore(traceIdFilter, JwtAuthenticationFilter.class)  // 又注册到 Security Filter Chain
```

**问题描述：**
TraceIdFilter 标注了 `@Component`，Spring Boot 会自动将其注册到 Servlet Filter Chain（默认 order 为 LOWEST_PRECEDENCE）。同时在 SecurityConfig 中又通过 `addFilterBefore` 注册到 Security Filter Chain。虽然 `OncePerRequestFilter` 保证同一请求只执行一次 `doFilterInternal`，但代码意图不清晰，且在某些边缘场景（如 forward/error dispatch）可能产生意外行为。

**影响分析：**
当前因 OncePerRequestFilter 和同一 Bean 实例的保护不会重复执行。但未来维护者可能误判行为，且如果需要控制 filter 在 Security 之外的路径上的行为时会产生困惑。

**修复建议：**
选择单一注册方式。推荐保留 `@Component` 和 `SecurityConfig` 注册，但通过 `FilterRegistrationBean` 禁用 Servlet 容器的自动注册。

```java
@Bean
public FilterRegistrationBean<TraceIdFilter> traceIdFilterRegistration(TraceIdFilter filter) {
    FilterRegistrationBean<TraceIdFilter> registration = new FilterRegistrationBean<>(filter);
    registration.setEnabled(false); // 禁止自动注册到 Servlet 容器
    return registration;
}
```

String message = ex.getConstraintViolations().stream()
